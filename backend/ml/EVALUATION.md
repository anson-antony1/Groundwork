# STOP-WORK forecast model: evaluation

Generated by `python -m backend.ml.train`. Do not edit by hand.

**Question:** at 6 PM, how likely is it that a real NWS alert of a STOP-WORK type (the same list the app's rules use) will cover this site during working hours tomorrow?

**Data:** 300 field sites x 3 years of days. Inputs are Open-Meteo's *archived forecasts* (the same variables the live app uses: forecast rain, max gust, max feels-like temperature, 7-day rain), plus location and time of year. Labels are real NWS alerts from the Iowa Environmental Mesonet archive.

**Split:** trained on 2023-07-01..2025-06-30 (219,300 site-days), tested on 2025-07-01..2026-06-30 (109,500 site-days), a full year the model never saw. STOP-WORK days: 5.8% of training rows, 4.6% of test rows.

## Design choices and limits

- **Why logistic regression ships, not gradient boosting:** every prediction can be explained as a sum of named factors (shown in the app as "what raised the risk"), it runs in pure Python inside the API with no new dependency, and its probabilities are calibrated without extra steps. The table above shows what the black-box model would add.
- **Advisory only.** The model never changes a status. Deterministic rules decide STOP WORK, so a missed forecast cannot silently clear a site.
- **The label is "an alert was issued", not "work was unsafe".** Tornado and severe-thunderstorm *watches* count because the app's rule stops work for them. Alerts cover whole counties or polygons, so a site can be labeled STOP WORK on a day its own weather was fine.
- **Archived forecasts are short-range.** Open-Meteo's historical forecasts are stitched from each model run's first hours, so they are somewhat more accurate than a real next-day forecast. Expect live performance a little below these numbers.
- **Calibration drifts with the year.** The test year had fewer STOP-WORK days than the training years (4.6% vs 5.8%), so mid-range probabilities read high; the top bin is close. Retraining each season, or recalibrating on the latest months, would fix most of it.
- **Florida is the exception.** There the model does not beat the rule score (see By region): summer thunderstorms hit almost every afternoon, and the four daily inputs cannot tell which afternoon. CAPE would help most.
- **The Hurricane Milton replay day (2024-10-09) is inside the training years**, so the app's replay shows an in-sample prediction. The fair test is the held-out year above.
- **Sites are not a random sample** (OpenStreetMap substations, about 5 per state), and nearby sites share storms, so the confidence intervals resample days, not rows.
- **Next inputs to try:** CAPE (thunderstorm energy) and precipitation hours from the same API would likely lift accuracy most, at the cost of a wider live snapshot.
